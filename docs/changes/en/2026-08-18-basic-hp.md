# Change: Basic HP and player death

## Objective

Implement Round 5 for Wizard Duel: consume the Round 4 `hit_flags` record as
real per-player HP. Each player starts with `PLAYER_START_HP = 3`; a valid
cross-fire hit removes one HP; a player at 0 HP is dead (not rendered, cannot
fire) while keeping its position and any missile already in flight. All of
this had to land inside the fixed 10-line overscan without breaking the
deterministic 262-scanline frame that Round 4 established.

## Added

* **`ProcessHitEffects`** (main.asm): runs at overscan init right after
  `ProcessCollisions`. Two damage blocks (one per player) decrement the HP
  of a hit player (`HIT_P0`/`HIT_P1`), skipping players already at 0 HP so
  HP never goes below zero. Then a **branchless dead-player fire lock**
  forces a dead player's FIRE bit in `fire_prev` to "pressed" using the ADC
  carry trick (`LDA hp; CLC; ADC #$FF` -> carry = alive), so `UpdateMissiles`
  never sees a rising edge from a dead player. The routine is page-aligned
  (`ALIGN 256`) so its four `BEQ`s can never gain a page-crossing cycle.
* **`p0_hp` / `p1_hp`** RAM bytes (2 bytes; RAM 49 -> 51), initialized to
  `PLAYER_START_HP` in `Reset`.
* **`PLAYER_START_HP = 3`** in `constants.inc` (plus `HIT_P0`/`HIT_P1`
  docstring updated: the flags are now consumed as damage). The gameplay
  logic never depends on the value being 3, only on comparing against zero.
* **BuildEvents HP gate**: a dead player contributes no P0/P1 events, so it
  is simply not drawn.
* **Tests**: `tests/test_hp.py` (13 tests) drives the real `ProcessHitEffects`
  assembly: initial HP, single/simultaneous hits, exact consumption (one hit
  = one HP), no underflow, stale `hit_flags` do not damage, death by hits,
  dead player not rendered / cannot fire / alive player unaffected, active
  missile survives owner death. `tests/test_frame_timing.py` gained a
  dead-player frame-stability test and the max-stress regression now tops up
  HP every frame (without that, Round 5 HP would kill both players during the
  3 boot frames and silently weaken the worst case).

## Changed

* `OVERSCAN_LOOP_COUNT` 8 -> 7 to absorb the new `ProcessHitEffects` JSR
  while keeping the overscan exactly 760 cycles (10 lines).
* The overscan comment block now documents the Round 5 cost window: from the
  kernel's last WSYNC (K) the fixed part (7 + 22 + 6 + 84 + 6 + 2 = 127) plus
  the variable body B in [60, 80] puts the first overscan WSYNC write at
  K + [187, 207], which lands on K + 228 on every path; 7 countdown WSYNCs
  reach K + 684 and the next frame's VSYNC lands on K + 760.
* RAM layout docstrings and docs: `p0_hp`/`p1_hp` inserted between `P1Y` and
  `ball_x`, shifting all subsequent zero-page addresses.
* `tools/emu6502.py` gained `EOR #imm` ($49) and `ORA zp` ($05) opcodes used
  by the fire lock.

## Technical Reasoning

### Why damage + fire lock live in one routine

The overscan is anchored by a fixed WSYNC countdown, so the work before the
first WSYNC only has to land on the same 76-cycle boundary on every path.
The Round 5 work is branchy (2 + 2 conditional branches per player plus the
40-cycle fire lock), but its total cost window is B in [60, 80] cycles, which
puts the first WSYNC write at K + [187, 207] and every path lands on K + 228.
On a real 6502 a taken branch costs +1 (and +1 more on a page crossing):
damage costs 8/13/17, total B in [62, 80], first write K + [190, 208], still
strictly inside (K + 152, K + 228]. Two separate routines (collision + hit
effects each with their own JSR) would have left only a 2-cycle upper margin;
combining them into one JSR gives the full window.

### Why the fire lock is branchless and re-applied every frame

`UpdateMissiles` overwrites `fire_prev` with the current button state during
every VBLANK, so a one-time lock would only hold for a single frame. The
branchless ADC carry trick recomputes the dead mask every overscan, so a dead
player's FIRE bit always reads as "pressed" when `UpdateMissiles` samples it
- a press can never be a rising edge. `tempCount` is reused as scratch; it is
safe because `ProcessCollisions` (and `ProcessHitEffects`) run before any
other user of the builder temps.

### Why hit_flags is read but not cleared

`ProcessCollisions` writes `hit_flags` every frame (from the latches) before
`ProcessHitEffects` runs, so a stale byte can never cause double damage; the
Round 4 test contract (`hit_flags` observable after the frame) is preserved.

### Why dead players keep moving

A dead player is not rendered (no events) and cannot fire, but `UpdatePlayers`
still moves it. This is unobservable on screen, keeps the VBLANK path simple,
and avoids a variable branch in a region whose margin we measured (~45 cycles
worst case, including the new BuildEvents gate).

## Rejected approaches

* **Two separate JSRs** (damage routine + fire-lock routine): only a 2-cycle
  upper margin on real hardware - too fragile.
* **A `fire_prev` lock set once at death**: `UpdateMissiles` overwrites the
  byte every VBLANK, so the lock must be recomputed per overscan.
* **HP displayed on screen / victory / game-over / restart**: out of scope;
  no HUD or round-transition system exists yet.

## Timing Impact

Before:
- Frame scanlines: 262 (19912 cycles), uniform under Round 4 max stress
- Overscan: `OVERSCAN_LOOP_COUNT = 8`, first WSYNC at K + 152
- VBLANK: no player-death work

After:
- Frame scanlines: 262 (19912 cycles), uniform under max stress (players kept
  alive) and with both players dead
- Overscan: `OVERSCAN_LOOP_COUNT = 7`, first WSYNC lands K + 228 on every
  path (write at K + [187, 207]); region still exactly 760 cycles
- VBLANK: BuildEvents HP gate adds ~10 cycles only on the alive path;
  measured worst-case poll exit leaves ~45 cycles of margin

## Known Limitations

* No HUD, victory/game-over transition or round restart: a dead player simply
  keeps its arena position and stops contributing.
* A dead player still consumes joystick input (moves, though invisible).
* The emulator does not model 6502 page-crossing penalties; the `ALIGN 256`
  on `ProcessHitEffects` is the hardware-only guarantee that its branches
  stay inside one page.
* `docs/benchmarks/baseline.json` still reflects the Round 1 state by design
  (the persisted baseline is only refreshed explicitly); regression compares
  against a fresh build of `main`.
