# Change: Paddles and ball (Round 2)

Date: 2026-08-16
Branch: `round-2-ball-paddles`

## Objective

Evolve the Round 1 technical base into a recognizable game shape: replace the
single-row sprite placeholder look with solid vertical paddles and add a TIA
Ball that moves continuously and bounces off the four edges of the play
area. No collisions, scoring, power-ups or player/ball interaction yet.

## Added

* `src/main.asm`:
  * `UpdateBall` (assembled at `$F103`): moves the ball one pixel per frame
    on both axes and reverses a direction when the ball reaches an exact
    arena edge, *before* moving, so the position is always clamped and can
    never wrap through an unsigned underflow.
  * `PositionBall` (assembled at `$F149`): horizontal placement of the ball
    using `RESBL` + `HMBL`, reusing the shared `PosObject` routine.
  * The kernel ball-enable block: every kernel line compares the line index
    against `ball_y` and writes `ENABL` (the enable value on the ball's row,
    `0` everywhere else).
  * `P0Sprite`/`P1Sprite` replaced with 12-byte solid rectangles of
    `%00111100` (4-pixel-wide paddles).
  * `Reset` initializes the ball state (`ball_x`, `ball_y`, `ball_dx`,
    `ball_dy`) and the ball hardware (`CTRLPF` for the 4-pixel size,
    `COLUPF` for the color).
* `src/constants.inc`: `BALL_WIDTH`, `BALL_SIZE_CTRLPF`,
  `BALL_X_MIN/MAX`, `BALL_Y_MIN/MAX`, `BALL_X_INIT`, `BALL_Y_INIT`,
  `BALL_COLOR`, `BALL_ENABLE`, `DIR_LEFT/RIGHT/UP/DOWN`.
* `tests/test_ball.py`: a small deterministic 6502 interpreter
  (`Mini6502`) executes the real `UpdateBall` bytes from the assembled ROM;
  tests cover diagonal movement, bounces on all four edges, a corner bounce,
  the bounds invariant over 2000 frames, initial state, RAM usage (7 bytes),
  kernel `ENABL` writes on both paths, and kernel page confinement.
* RAM variables `ball_x` (`$83`), `ball_y` (`$84`), `ball_dx` (`$85`),
  `ball_dy` (`$86`).

## Technical Reasoning

* **Ball is one scanline tall**: the TIA Ball is a 1-pixel-tall object; it
  is drawn by latching `ENABL` on the scanline matching `ball_y`. Because
  `ENABL` latches for the *following* scanline, the kernel must rewrite it
  every line: the enable value on the ball's row and `0` everywhere else,
  or the ball would stick on screen. The row test is a simple `CMP ball_y`
  + `BNE`, costing 15 cycles on the ball's line and 13 elsewhere.
* **Bounce before moving**: checking the edge *before* the move guarantees
  the stored position stays inside `[MIN, MAX]`. Moving first and clamping
  afterward would behave identically at the edges but adds a redundant move;
  reversing first is also what makes the "reverse and step away" behavior
  exact rather than wrapping through `$FF`.
* **`PositionBall` passes `ball_x + 1`**: the TIA delays player graphics by
  one extra color clock, so the same `RESP` input places the ball one pixel
  to the left of where a player would render. The +1 compensation keeps the
  on-screen ball at the requested `ball_x`.
* **Ball color/size come from shared TIA registers**: the ball is colored by
  `COLUPF` and sized by `CTRLPF` D5:D4 (`%10` = 4 pixels). This round sets
  them once at reset; nothing else in the kernel writes to the playfield, so
  there is no conflict.
* **New code fits the page padding**: the ball code and the paddle sprites
  fit in the padding space reserved before the page-aligned
  `fineAdjustBegin`; ROM usage stays at 528 bytes.
* **Interpreter tests replace runtime probing for the ball**: ball motion is
  fully deterministic (fixed speed, edge bounces), so executing the assembled
  `UpdateBall` on a small 6502 interpreter is a stronger, CI-safe check than
  screenshot analysis. Stella remains the reference for visual placement.

## Timing Impact

Before (Round 1):
- Frame scanlines: 262
- Kernel worst/best: 56 / 44 cycles (slack 20)

After (Round 2):
- Frame scanlines: 262 (unchanged)
- Kernel worst: 71 / 76 cycles (both paddles drawn + ball on), slack **5**
- Kernel best: 57 cycles (both paddles blank + ball off)
- Ball block: 15 cycles on the ball's line, 13 otherwise; all eight
  combinations are enumerated and asserted by the test suite.
- `GRP0` ~cycle 24, `GRP1` ~cycle 47, `ENABL` ~cycle 63 of each scanline.

The slack dropped from 20 to 5 cycles. This is the deliberate cost of adding
a hardware object to the visible kernel; it was verified in Stella that the
ball renders exactly one scanline tall and moves smoothly.

## Memory Impact

Before (Round 1):
- ROM: 528 bytes
- RAM: 3 bytes

After (Round 2):
- ROM: 528 bytes (ball code + paddles fit the reserved page padding)
- RAM: 7 bytes (+4: `ball_x`, `ball_y`, `ball_dx`, `ball_dy`)

## Regression result

Run against the persisted Round 1 baseline:
- Kernel worst case 56 -> 71 (+15) and slack 20 -> 5 (-15): two **soft**
  warnings (thresholds +4 / -4), CI still PASS (exit 0).
- RAM 3 -> 7 (+4): equals the warning threshold, so no RAM warning.
- ROM unchanged: no warning.

## Known Limitations

* No collision between ball and paddles yet; the ball passes through the
  paddles. That is intentional in this round.
* Ball speed is a fixed 1 px/frame; no acceleration or player influence.
* The `-holdjoy*` Stella command-line options are unreliable (they release
  after ~0.8 s); automated runtime joystick input used `xdotool keydown`
  instead.
* Stella's debugger console cannot be captured in a headless session (no
  stdout from the debugger, `saveSes` produced no readable file, and debug
  mode snapshots are black); runtime validation used pixel analysis of live
  window captures.
* Kernel slack is now 5 cycles: future kernel work has little margin and
  must be validated carefully.
